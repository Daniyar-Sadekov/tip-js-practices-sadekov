## 1. Цель работы

Подключить браузерный интерфейс управления задачами к HTTP API с поддержкой полного CRUD (`GET`, `POST`, `PATCH`, `DELETE`), управлением состояниями загрузки (`loading`, `ready`, `empty`, `error`), блокировкой повторных мутаций и защитой от устаревших ответов через `AbortController`.

## 3. Реализация

### 3.1. HTTP-клиент

`src/api-client.js` поддерживает методы `GET`, `POST`, `PATCH`, `DELETE`, `HEAD`. При передаче `body` автоматически добавляется заголовок `Content-Type: application/json` и выполняется `JSON.stringify(body)` (для `GET` передача `body` запрещена). Успешный статус `204 No Content` сразу возвращает `null` без попытки вызвать `response.json()`. Реализованы тайм-аут (`kind: "timeout"`) и внешняя отмена через `AbortSignal` (`kind: "aborted"`).

### 3.2. Доменный API

`src/task-api.js` реализует `getTasks`, `getTaskById`, `getCategories`, `loadInitialData`, `createTask` (`POST /tasks`), `updateTask` и `setTaskCompleted` (`PATCH /tasks/:id`), `deleteTask` (`DELETE /tasks/:id`, ожидает `204`) и `resetData`. Валидация схемы ответа (поля задачи/категории, уникальность `id`, `meta.total`) выполняется внутри доменного модуля до передачи данных в контроллер.

### 3.3. Состояния интерфейса

`src/app-controller.js` и представление управляют четырьмя явными состояниями списка: `loading` (идёт запрос), `ready` (получен непустой список), `empty` (успешный ответ с 0 задач) и `error` (ошибка загрузки с возможностью повтора). Отменённый (`aborted`) запрос не переводит интерфейс в `error`.

### 3.4. Изменение данных

Все мутации (`create`, `update`, `toggleTask`, `delete`, `reset`) проходят через единый метод `_mutate`: блокируют элементы управления (`setMutationPending(true)`), отправляют запрос на сервер, выводят уведомление об успехе и заново запрашивают текущий отфильтрованный список (`_loadCurrentTasks()`), в `finally` снимая блокировку.

### 3.5. Защита от устаревшего ответа

Перед каждой загрузкой `_loadCurrentTasks` отменяет предыдущий незавершённый запрос вызовом `this.loadController?.abort()`, создаёт новый `AbortController` и увеличивает счётчик `loadId = ++this.loadId`. После `await` проверяется `if (loadId !== this.loadId) return;`, что полностью исключает применение запоздавшего ответа.

## 6. Ответы на контрольные вопросы

1. *Почему `fetch` не отклоняет Promise при ответе 404?*
   Потому что HTTP-ответ со статусом `404` означает, что сетевой обмен состоялся и сервер корректно ответил; `fetch` отклоняет `Promise` только при сетевой ошибке, недоступности сервера или отмене запроса (`AbortError`), поэтому статус нужно явно проверять через `response.ok`.
2. *Почему ответ 204 нельзя разбирать вызовом `response.json()`?*
   Статус `204 No Content` по стандарту HTTP не имеет тела ответа; попытка распарсить пустое тело через `response.json()` вызовет `SyntaxError`.
3. *Чем состояние `empty` отличается от `error`?*
   `empty` — это успешный ответ сервера (`200 OK`), в котором по текущим фильтрам найдено 0 задач; `error` — сбой получения данных (сетевая ошибка, HTTP 4xx/5xx, тайм-аут или битый ответ).
4. *Зачем отменять предыдущий запрос при смене фильтров?*
   Чтобы не тратить ресурсы и избежать состояния гонки (race condition), когда более ранний медленный ответ придёт позже нового и перезапишет актуальный список на экране.
5. *Почему после мутации список повторно запрашивается у API?*
   Источником истины является сервер: после `POST`/`PATCH`/`DELETE` задача может перестать удовлетворять активным фильтрам (например, `completed=false`), измениться `meta.total` или сгенерироваться `id`, поэтому повторный `GET` гарантирует согласованность интерфейса с сервером.
