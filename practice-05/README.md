## Эксперимент с очередями выполнения

| Этап | Порядок меток | Объяснение |
|---|---|---|
| Прогноз до запуска | `A → B → C → D → E → F` | Сначала выполняется синхронный стек (включая тело `async`-функции до первого `await`), затем очередь микрозадач (`Promise.then` и продолжение после `await`), и только потом макрозадача таймера (`setTimeout(..., 0)`). |
| Фактический результат | `A → B → C → D → E → F` | Полностью совпало с прогнозом. |

Фактический вывод `npm run example:order`:

```text
A: синхронный код
B: начало async-функции
C: конец синхронного кода
D: обработчик Promise
E: продолжение после await
F: задача таймера
```

- Синхронный код: `A`, `B` (начало `async`-функции до `await`), `C`.
- Очередь микрозадач: `D` (`.then`) и `E` (продолжение после `await`).
- Таймер с задержкой `0` (`F`) попадает в очередь макрозадач и выполняется только после освобождения стека и полного исчерпания очереди микрозадач.
- Удаление одного обработчика `Promise` убирает соответствующую микрозадачу, но не меняет приоритет микрозадач над макрозадачами.

## Организация кода

| Файл | Ответственность |
|---|---|
| `api/server.mjs` | Готовый учебный HTTP API (чтение задач и категорий, фильтрация, отладочные маршруты). |
| `src/api-client.js` | Универсальный HTTP-клиент: `ApiError`, `buildUrl`, `createApiClient`, `requestJson`, тайм-аут, `AbortSignal`, классификация ошибок. |
| `src/task-api.js` | Доменный клиент (`getTasks`, `getTaskById`, `getCategories`, `loadInitialData`), нормализация фильтров и проверка схемы ответов. |
| `src/variant.js` | Конфигурация индивидуального варианта (`variantNumber = 7`, `variantFilters = { q: "провер" }`). |
| `src/main.js` | CLI-сценарий запуска: запрос по фильтрам варианта и демонстрация перехвата ошибки `404`. |

`fetchFn` передаётся в `createApiClient` аргументом, чтобы модульные тесты могли подменять сеть без реального HTTP-сервера. HTTP-ошибки (`!response.ok`) проверяются отдельно, потому что `fetch` отклоняет `Promise` только при сетевом сбое или отмене, а `404`/`503` считает успешным получением `Response`. JSON после разбора проверяется по схеме, чтобы клиент не принял неполный или искажённый ответ сервера за валидные доменные данные.

Проверяются: структура каждой задачи (`id`, `title`, `completed`, `priority`, `categoryId`), уникальность `id` в массиве, совпадение `meta.total` с длиной/контрактом и структура каждой категории.

## Последовательная и параллельная загрузка

В `loadInitialData` запросы задач и категорий запускаются одновременно через `Promise.all([getTasks(...), getCategories(...)])`, а не двумя последовательными `await`. При искусственной задержке `/debug/delay` последовательное выполнение суммирует время обоих запросов ($t_1 + t_2$), тогда как `Promise.all` ждёт лишь более медленный из них ($\max(t_1, t_2)$), поскольку сетевые ожидания перекрываются во времени.
