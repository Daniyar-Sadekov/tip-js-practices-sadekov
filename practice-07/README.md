## Результат

Реализован компонентный интерфейс управления задачами на React (Vite): отображение статистики по всему набору, мгновенная клиентская фильтрация по статусу («Все», «В работе», «Завершённые»), приоритету, категории и поисковой подстроке, условный рендеринг заглушки при пустом списке, а также создание, редактирование, переключение статуса и удаление задач. Состояние хранится в оперативной памяти компонента `App`, поэтому после перезагрузки страницы данные возвращаются к исходному набору.

## Компоненты и состояние

- Владелец `tasks`, `filters` и `editingId` — корневой компонент `App.jsx` (подъём состояния вверх, чтобы статистика, фильтры, список и форма работали с единым источником истины).
- Владелец `draft` и `errors` — компонент формы `TaskForm.jsx` (локальное состояние ввода до отправки; при смене редактируемой задачи форма пересоздаётся/сбрасывается через `key`).
- Вниз по дереву передаются данные и колбэки через `props` (`TaskFilters` получает `filters` и `onChange`, `TaskList` — `tasks`, `onEdit`, `onToggle`, `onDelete`).
- Производные данные (`visibleTasks` через `selectTasks(tasks, filters)` и `stats` через `getTaskStats(tasks)`) не дублируются в `useState`, а вычисляются напрямую на каждом рендере.

## Контрольные вопросы

- **Зачем выносить состояние в `App`?** Чтобы несколько дочерних компонентов (`TaskFilters`, `TaskList`, `TaskForm`, статистика) использовали одни и те же актуальные данные и не рассинхронизировались.
- **Почему производные данные не хранят в `useState`?** Хранение `visibleTasks` или `stats` в отдельном состоянии создаёт дублирование и риск расхождения при изменении `tasks` или `filters`.
- **Зачем нужен стабильный `key={task.id}` в `.map()`?** React использует `key` для сопоставления элементов между рендерами; индекс массива ломает соответствие при фильтрации и удалении, а уникальный `task.id` сохраняет корректное обновление DOM.

## Вывод

Освоен компонентный подход в React: однонаправленный поток данных (`props` вниз, колбэки вверх), иммутабельное обновление состояния через `useState`, условный рендеринг и вычисление производных данных. Все 28 тестов и production-сборка `vite build` проходят без ошибок. При подключении API в ПР8 локальный массив `tasks` и синхронные операции заменятся асинхронным хуком `useTaskData` и запросами к серверу.
